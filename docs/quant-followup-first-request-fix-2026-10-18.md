## 첫 접속 지연의 원인과 수정

실제 JVM을 재시작한 뒤 첫 요청을 끝까지 측정했습니다. 스레드 덤프와 MariaDB 실행계획에서
`StockQuantModelHealthService → findQuantModelHealth` 대기를 확인했습니다. 약 222만 행의
예측 테이블을 모델별로 반복 전체 읽기하고, 약 735만 행의 기여도 테이블도 전체 읽기했습니다.
상태 집계는 넓은 과거 스냅샷 행을 다시 가져왔고, PIT 출처 점수는 약 137만 행에서 동일한
문자열 분류를 매번 반복했습니다. 인메모리 30초 캐시가 비어 있을 때 이 작업이 드러났습니다.

수정은 조회 경로에 한정했습니다.

1. 모델·종목·기간에 맞는 예측 조회 및 상태 집계용 covering index 7개를 추가했습니다.
   기존 업무 인덱스나 데이터는 삭제하지 않았습니다. 이 작업 초기에 만든 좁은 임시 인덱스
   2개만 대체했습니다. 비용은 추가 인덱스 저장공간과 쓰기 작업량입니다.
2. PIT 출처 점수는 먼저 같은 출처의 행 수를 모은 뒤 기존 분류를 적용합니다.
   원래 행 기준 평균을 유지하도록 출처별 행 수로 가중했습니다. 단순한 출처 평균이 아닙니다.
   기존 필터, 분류 우선순위, 겹치는 분류 수, 빈 입력의 0건/점수 미확인도 유지했습니다.

가격, 예측 공식, 학습 결과, 날짜, 자료 출처, 최신성 제한, 외부 수집 설정은 바꾸지 않았습니다.
페이지 요청은 계속 DB 조회만 사용합니다. 화면을 미리 생성해 지연을 숨기지 않았습니다.

기존 DB용 재실행 가능한 migration:
`src/main/resources/db/quant-health-query-indexes.sql`.
신규 DB용 `schema-mariadb.sql`에도 동일한 정의를 반영했습니다. 현재 로컬 DB에는 직접 적용했고
다시 실행해도 성공함을 확인했습니다. SQL 초기화가 꺼진 다른 DB에는 이 migration을 명시적으로
적용해야 하며, 파일을 복사하는 것만으로 이미 존재하는 테이블이 바뀌지는 않습니다.

- `StockDataQualityService.java:180`은 quote의 `quoteTime` 대신 `fetchedAt`으로 최신성을 판정한다. 오늘 받은 오래된 시세가 신선한 데이터로 취급될 수 있다.
- `StockQuantModelHealthService.java:159`는 Signal/품질 행이 있으면 날짜 검사를 건너뛴다. `:201`은 오래된 배치라도 성공 상태면 정상으로 표시한다.
- 개선: 수집 성공과 시장 데이터 최신성을 별도 평가. 거래소 캘린더 기준일, 종목 커버리지, 부분 실패를 검사. 오래된 입력의 신규 계산 시각으로 신뢰도를 높이지 않는다.

### 14. 과거 구성종목과 benchmark에 대용 데이터가 남음

- `StockBacktestMapper.xml:2253`의 과거 학습 조회는 현재 편입종목 조건을 사용한다. 과거에 존재했으나 빠진 기업을 제외하는 생존편향 위험이 있다.
- DB의 구성종목에는 `CURRENT_MEMBERSHIP_PROXY`가 다수 존재한다. Wikipedia 변경 이력도 존재하지만 모든 과거 날짜를 공식 PIT 데이터로 보장하지 않는다.
- benchmark 3개 지수 모두 `MARKET_SNAPSHOT_WEIGHTED` 출처다. 공식 지수 total return으로 표기/해석하면 안 된다. 주식수도 SEC 이외 current proxy가 남는다.
- 개선: 당시 유니버스/상장폐지/기업행사 자료 보강, benchmark provenance 표시, 가격수익과 배당포함 수익 정의 통일. 이 부분은 일부 문서에 이미 적힌 모델 한계이기도 하다.

### 15. 원화 환산과 표기 기준 불일치

- `StockMarketViewService.java:18`, `StockHeatmapViewService.java:21`은 환율 1,365원을 상수로 사용한다. 실제 원화 현재가처럼 보이지만 환산 가정/날짜를 보여주지 않는다.
- 일봉을 쓰는 경우 화면은 여전히 현재가라고 표시한다. 템플릿 일부 설명은 v8인데 조회 모델은 v9다 (`templates/dashboard.html:92`, `:179`).
- 개선: 달러 기본 표시 또는 날짜가 있는 DB 환율 사용. 종가/장중가·기준일·모델 버전·확률의 사건 정의를 화면과 코드에서 일치.

### 16. 화면 캐시가 없을 때 요청 안에서 전체 연구 계산

- `StockPortfolioBacktestService.java:138`, `:235`는 저장본이 없으면 최대 100,000행과 모델 입력을 읽어 여러 전략을 계산한다. 동시에 들어오는 cold request를 하나로 합치는 제어도 없다.
- 현재 HTTP가 빠른 것은 저장본 경로의 단발 관찰이다. 초기 구축/버전 변경/저장본 오류 때의 부하를 보장하지 않는다.
- 개선: 계산을 제한된 백그라운드 작업으로 넘기고 요청에는 최신 저장본 또는 준비 상태를 제공. 지수·버전당 동시 재계산 한 개로 제한.

## 유지할 장점

- 원천별 일봉 저장과 canonical 계열 분리, OHLC/거래량 검사가 이미 존재한다.
- 현재 Signal 계산은 DB 캐시를 사용하며, 지수별 화면과 예상수익이 저장된다.
- 실제 LIVE와 역사 재구성 신호 구분, 모델 버전, 위험/공분산/기여도·건강 상태 기반이 있다.
- 평가/승격 gate가 있어 오류 수정 후 검증 체계를 강화할 자리가 마련되어 있다.
- 전체 Java 테스트가 실행 가능하다. 다만 문자열 계약 테스트와 단순 사례의 통과는 금융 의미의 정확성을 보장하지 않는다.

## 개선 순서와 완료 기준

1. **가격·데이터·캐시 일관성**: APH가 실제 `/quant`에서 올바른 기준일과 값으로 표시되고 목록/상세/Signal이 동일 정책을 사용. CRM 같은 더 최신 시세와 단일 일봉 fallback, 분할/병합 fixture 검증. 오래된 데이터는 명시적 상태로 표시.
2. **학습·평가 신뢰성**: 라벨 성숙/보정 cutoff, 동일 benchmark, eligible test 모집단, 커버리지 분모를 수정. 미래 값을 바꿔도 그 이전 시점 예측이 변하지 않는 회귀 테스트를 통과.
3. **투자 회계**: 실제 일별 P&L 또는 비중이 명확한 cohort 회계로 재계산. 겹친 보유기간·수수료·슬리피지·배당·상장폐지 fixture와 독립 계산 대조.
4. **새 버전으로 재검증**: 기존 결과를 덮어써 성능을 소급 정당화하지 않고 기준 데이터/코드 버전과 함께 재평가. 충분한 out-of-sample 기간과 품질 기준을 통과한 뒤 신뢰 수준을 변경.
5. **운영 경로 분리**: 페이지 요청은 읽기 전용, 수집/계산/발행 결과는 단계별 기록. 부분 실패가 전체 정상처럼 표시되지 않아야 함.

## 기반 수정 후 추가하면 좋은 기능

| 기능 | 사용자에게 주는 가치 | 필요한 선행 조건 |
|---|---|---|
| 종목별 데이터 기준일·신뢰 상태 | 오래된 가격/예측을 즉시 구분 | quoteTime, 거래일, 조정 버전 통일 |
| Signal 변화와 근거 추적 | 점수가 왜 바뀌었는지 확인 | 입력 버전·요인별 기여도 이력 |
| 절대 상승확률 / 지수 초과확률 분리 | 확률의 의미를 오해하지 않음 | 학습 목표와 평가 목표 통일 |
| 실전 모의운용 기록 | 당시 발표한 예측의 이후 성과 확인 | 변경 불가능한 예측 저장, 비용 반영 |
| 모델별/국면별 비교 화면 | 새 모델이 실제로 나아졌는지 판단 | 검증된 OOS 평가·동일 표본 |
| 중복 노출·섹터 집중·유동성 경고 | 고득점 종목을 모아도 생기는 위험 확인 | 최신 공분산/거래량·제약 진단 |
| 수집 실패·데이터 지연 경고 | 숫자가 낡은 상태를 빠르게 발견 | 단계별 배치 결과·시장 캘린더 |

새로운 대형 AI 모델 도입보다 위 데이터·평가 결함 수정의 우선순위가 높다. 현재 평가 기록은 유효 월 0의 데이터 부족 상태이므로 모델 성능이 검증됐다고 말할 수 없다.

## 재현 자료와 한계

- `tmp/QuantAuditProbe20261017.java`: 실제 production 수학 클래스를 호출하는 합성 입력 검증. 실행: `java --class-path target/classes tmp/QuantAuditProbe20261017.java`.
- 결과: 사후 예측 + benchmark 한 거래일만 존재하는 불완전 구간을 수락, PIT 위반 0. 겹치는 20일 수익률 두 개를 +21%로 복리 계산.
- DB는 SELECT/집계만 실행했다. 실제 상세 페이지는 외부 호출·품질 저장 경로가 있어 호출하지 않고 코드로 검수했다.
- 모든 파일의 모든 분기, 실제 기업행사 공급사 계약, 부하·침투 테스트, 전체 과거 모델 재학습/실거래 수익 검증까지 수행한 것은 아니다. 주요 데이터→모델→평가→화면 경로를 검토했다.
- 이번 검수로 발견한 결함을 수정한 것은 아니다. 기존 가격 변경도 추가 보완 및 실행 환경 반영이 필요하다.
